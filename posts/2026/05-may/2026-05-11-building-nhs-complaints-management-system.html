Building a Complaints Case Management System

11 May 2026 · 3 min read · 🔨 Building

Complaint handling in healthcare still runs largely on spreadsheets, shared inboxes and a lot of chasing. Over the last few months I've built a full-stack case management system to change that. This post covers why I built it, the principle behind it and one lesson I learned the hard way.

The problem worth solving

Large hospital trusts receive thousands of complaints and PALS queries every year. Each formal complaint has a response deadline, and a late or poor response can end up with the Parliamentary and Health Service Ombudsman.

When the work runs on spreadsheets and inboxes, deadlines slip and coding varies from one person to the next. Spotting a pattern, such as one ward generating repeat complaints about the same issue, relies on someone reading everything and keeping it in their head. I wanted one place to run the whole process, capturing structured data from the start so an organisation can learn from it.

From prototype to a proper stack

I started in Streamlit, which is great for exploring data but not for a multi-user workflow app. I rebuilt it as a Python API using FastAPI and SQLAlchemy, with a Next.js and TypeScript front end. Development uses synthetic data only.

The AI suggests, a person decides

This is the design decision I'm most deliberate about. The AI does nothing on its own. Every suggestion it makes is reviewed and confirmed by a member of staff before it becomes part of the case record.

The stakes are high, staff are rightly sceptical of automation in this kind of work, and any model will make mistakes. The review step catches them. The AI earns trust by being useful, not by being autonomous.

A bug worth sharing

One problem cost me longer than it should have. My reporting endpoints kept throwing SQLAlchemy's DetachedInstanceError. I was building the response after the database session had closed, so the ORM objects could no longer load their attributes. The fix was to do all attribute access inside the session block: 

# Wrong - attributes accessed after db.close()
with get_db() as db:
    records = db.query(Record).all()

for record in records:
    for item in record.items:  # DetachedInstanceError here
        ...

# Correct - all access inside the context
with get_db() as db:
    records = db.query(Record).all()
    for record in records:
        for item in record.items:
            # process here, before db.close()
            ...

The error message pointed me towards a relationship configuration problem, which sent me the wrong way for a while. It was a session lifecycle problem all along.

What I took from it

The most valuable thing I can do with data science skills in this space isn't necessarily training models. It's building the systems that capture clean, structured data in the first place. The insights are only as good as the data feeding them.
